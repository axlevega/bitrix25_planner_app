# Деплой на сервер по FTP

## Два варианта разработки

### Вариант A: Локальный фронт → удалённый бэкенд

Бэкенд уже на сервере, Vue запускаете у себя на ПК.

1. В каталоге **frontend** создайте или отредактируйте **`.env`** (скопируйте из `frontend/.env.example`).
2. Задайте полный URL API вашего сервера:
   ```
   VITE_API_BASE_URL=https://ваш-домен.ru/api
   ```
   (без слэша в конце; замените на ваш домен и путь к API).
3. Запустите фронт локально: `cd frontend && npm run dev`.
4. В браузере откройте указанный Vite-адрес (обычно http://localhost:5173). Запросы к API пойдут на удалённый сервер.

**CORS:** в `backend/public/.htaccess` и в корневом `deploy/root.htaccess` добавлены заголовки CORS (`Header always set`), они отдаются на все ответы, в т.ч. при 401 от .htpasswd. **Preflight (OPTIONS) должен возвращать HTTP 2xx** — иначе браузер выдаст «Response to preflight request doesn't pass access control check: It does not have HTTP ok status». В бэкенде подключение к БД выполняется только в обработчиках маршрутов, а не при регистрации, поэтому OPTIONS не обращается к БД и возвращает 204. Если у вас включена авторизация по .htpasswd в `backend/public/.htaccess`, OPTIONS должен проходить без логина: замените `Require valid-user` на блок `<RequireAny> Require method OPTIONS / Require valid-user </RequireAny>` (пример в комментариях в `backend/public/.htaccess`). После изменений перезалейте соответствующий `.htaccess`.

### Вариант B: Всё на сервере — деплой и тест там

Соберите и залейте проект на сервер, тестируйте по домену (фронт и API на одном домене — без CORS).

1. Настройте деплой по FTP (см. ниже).
2. Выполните `npm run deploy` — зальются backend и собранный frontend (frontend/dist).
3. На сервере настройте БД, `.env`, выполните `composer install` в `backend`, при необходимости примените миграции.
4. Открывайте сайт по домену: фронт и API будут на одном источнике (например `https://ваш-домен.ru` и `https://ваш-домен.ru/api`).

При деплое сборка фронта (`npm run build` в `frontend/`) читает **`frontend/.env`**. Чтобы после деплоя запросы шли на тот же домен, в **`frontend/.env`** задайте `VITE_API_BASE_URL=/api` или оставьте пустым — в коде используется `baseURL || '/api'`, так что в обоих случаях запросы пойдут на `/api` того же домена.

## Локально (откуда запускается деплой)

1. В корне проекта скопируйте `.env.example` в `.env`.
2. Заполните переменные FTP (и при необходимости DB для локальной разработки):
   - `FTP_HOST` — хост FTP-сервера
   - `FTP_USER` — логин
   - `FTP_PASSWORD` — пароль
   - `FTP_PORT` — порт (по умолчанию 21)
   - `FTP_SECURE=true` — для FTPS (TLS)
   - `FTP_REMOTE_DIR` — корневой путь на сервере (например `/public_html`)
   - `FTP_REMOTE_BACKEND` — подкаталог для бэкенда (по умолчанию `backend`)
   - `FTP_REMOTE_FRONTEND` — подкаталог для статики фронта (по умолчанию `public`)

3. Установите зависимости в корне и во фронте:
   ```bash
   npm install
   cd frontend && npm install && cd ..
   ```

4. Запуск деплоя:
   ```bash
   npm run deploy
   ```

Скрипт собирает фронт и загружает по FTP:
- каталог **backend** (без `vendor`, `.env`, `.env.local`) в `FTP_REMOTE_DIR/FTP_REMOTE_BACKEND`;
- каталог **frontend/dist** в `FTP_REMOTE_DIR/FTP_REMOTE_FRONTEND`;
- корневой **.htaccess** в `FTP_REMOTE_DIR` (файл-шаблон: `deploy/root.htaccess`).

Файлы `.env`, `backend/.env`, `backend/.env.local` **не загружаются** — данные БД и секреты на сервере хранятся отдельно.

### Роутинг на виртуальном хостинге (public_html)

Корневой `.htaccess` настраивает:
- запросы **/api** и **/api/** → `backend/public/index.php` (API);
- запросы к существующим файлам/папкам в каталоге фронта → отдача из него;
- всё остальное → `public/index.html` (SPA, Vue Router).

Имена каталогов (`backend`, `public`) подставляются из `FTP_REMOTE_BACKEND` и `FTP_REMOTE_FRONTEND`. Для стандартного деплоя в `/public_html` после деплоя при открытии домена должна открываться страница приложения.

## На сервере после деплоя

### Требования: PHP 8.1+

Бэкенд требует **PHP 8.1 или выше**. Если на хостинге по умолчанию старая версия (например 5.6), в панели хостинга нужно переключить версию PHP для сайта на 8.1 или 8.2 (cPanel → «Select PHP Version», Plesk → «PHP version» и т.п.). Без этого `composer install` выдаст ошибку «your php version does not satisfy that requirement».

Если при `composer install` мешает глобальный плагин (например `fxp/composer-asset-plugin`), запустите:
```bash
composer install --no-plugins
```

### Данные подключения к БД

Они **не участвуют в деплое** и не попадают в git. Файл `.env` нужно **создать вручную на сервере**.

**Рекомендуемый вариант:** создайте на сервере файл **`backend/.env`** (т.е. рядом с папкой `public/` и файлами `src/`, `bootstrap.php` внутри `backend/`). Например, при деплое в `public_html` полный путь будет: **`public_html/backend/.env`**.

Содержимое (подставьте свои данные от хостинга):

```env
DB_HOST=localhost
DB_PORT=3306
DB_NAME=ваша_база
DB_USER=ваш_пользователь_бд
DB_PASSWORD=ваш_пароль_бд
```

Без кавычек, без пробелов вокруг `=`. Остальные переменные (BITRIX24_WEBHOOK_URL и т.д.) можно добавить по необходимости.

**Альтернативы:** можно положить `.env` в корень сайта (каталог, в котором лежат `backend/` и `public/`) или назвать файл `backend/.env.local` — оба варианта подхватываются `bootstrap.php`.

После первого деплоя на сервере нужно один раз выполнить `composer install` в каталоге `backend` (каталог `vendor` по FTP не заливается). Без этого запросы к `/api/` возвращают **500** (нет autoload).

**Если /api/ отдаёт 500:** откройте вкладку «Сеть» в инструментах разработчика браузера, выберите запрос к `/api/` или `/api/departments` и посмотрите тело ответа (JSON) — там поле `message` с текстом ошибки PHP. Убедитесь, что на сервере есть `.env` с корректными `DB_*` и что выполнен `composer install` в каталоге `backend`.

**Отладка подключения к БД:** откройте в браузере `https://ваш-домен/api/debug-db`. Ответ покажет: по каким путям искался `.env`, какие файлы найдены (`env_files_found`), установлены ли переменные `DB_HOST`, `DB_USER`, `DB_NAME`, `DB_PASSWORD` (да/нет, без значений), и текст ошибки подключения (`connection_error`), если оно не удалось. По этим данным можно понять, что именно не так (файл не там, переменные не подхватились, неверные учётные данные и т.д.). В продакшене эндпоинт можно потом отключить или защитить.

**Bad Gateway при «Синхронизировать сейчас»:** синхронизация с Bitrix24 может занимать 1–5 минут (много запросов к API, пагинация, задержки). В обработчике POST `/api/sync` выставлены `set_time_limit(300)` и увеличен лимит памяти — этого обычно хватает. Если всё равно приходит 502/504 Bad Gateway, обрывает запрос **прокси или веб-сервер** (nginx, Apache proxy) по своему таймауту (часто 60 с). Варианты: попросить хостинг увеличить таймаут (например `proxy_read_timeout` в nginx); либо запускать синхронизацию по cron, а кнопку использовать только для «лёгких» проверок.
