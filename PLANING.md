# Планирование нагрузки специалистов — техническое задание и видение продукта

## 1. Видение продукта

**Продукт** — инструмент планирования на основе данных из Bitrix24, замена ручной «шахматки» в Google Таблицах. Все данные (активные задачи, плановые трудозатраты, дедлайны, **учёт времени по дням** — кто сколько часов трекал по каждой задаче в каждый день) подтягиваются из Bitrix24; ручной ввод минимизирован.

**Ключевая ценность:** один экран — **сетка (шахматка)**: строки — активные задачи по проектам, колонки — специалист, проект, плановые часы, плановый дедлайн, затем колонки по рабочим дням (на выбранный период, в т.ч. на год вперёд). В ячейке дня — часы из Bitrix24 (кто в какой день трекал время по этой задаче). Руководитель видит актуальную картину без переноса данных из B24 вручную.

**Ранее:** планирование «в таблицах и чатах»; теперь — единая модель: кто чем занят, по каким задачам и в какие дни учтено время, связь с задачами Bitrix24 в реальном времени.

**Важные ограничения и принципы:**
- Специалисты работают **только с задачами** Bitrix24; другие сущности Bitrix24 (сделки, лиды, контакты и т.д.) не рассматриваются.
- **Единица трудозатрат** — только **рабочий час**. Никаких процентов от фондов, бюджетов или оборота: все планы и факты в часах.
- В компании есть **регулярные услуги** и **флайт-проекты** (разовые работы); один специалист (в т.ч. фуллстек) может заниматься и тем и другим — в приложении должна быть возможность задавать **лимиты часов по типам работ** (см. ниже).
- **Минимизация ручного ввода:** максимальная автоматизация за счёт данных из Bitrix24 (сотрудники, задачи, время выполнения, дедлайны, проекты задач и т.д.).

## 2. Целевая аудитория и роли

| Роль | Задачи | Что важно в продукте |
|------|--------|----------------------|
| **Руководитель подразделения** (SEO, разработка, дизайн) | Распределение людей по проектам, контроль загрузки отдела, найм/ресурсы | Свод по отделу, прогноз на 2–3 месяца, перегруз/недогруз, привязка к задачам Bitrix24 |
| **Проектный менеджер** | Планирование проектов, сроки, запрос ресурсов у отделов | Загрузка по отделам/специалистам, «окна» для новых задач, связь с задачами Bitrix24 |

Опционально в будущем: **владелец/директор** — сводная картина по всем отделам и прогноз по компании.

## 3. Решаемые проблемы и подход

### 3.1. Проблема 1: Планирование нагрузки и прогноз на 2–3 месяца

**Суть:** Нет единой картины, кто чем занят в среднесрочной перспективе; сложно планировать новые проекты и видеть «окна» для срочных задач.

**Решение в продукте:**

- **Единица планирования** — трудозатраты **только в рабочих часах** на специалиста/отдел с привязкой к периоду (день/неделя/месяц) и к задачам Bitrix24 (другие сущности Bitrix24 не используются).
- **Горизонт планирования:** минимум 2–3 месяца вперёд с возможностью просмотра по неделям и месяцам.
- **Источники данных для прогноза:**
  - **Задачи из Bitrix24** — сроки, ответственные, оценка/факт времени, проекты задач; всё подтягивается автоматически, ручной ввод сводится к минимуму.
  - При необходимости — минимальное ручное планирование (резерв, внутренние задачи, не отражённые в Bitrix24) и учёт отпусков/недоступности (по возможности из календаря Bitrix24).
- **Вид прогноза:** таблица/канбан по специалистам и по отделам, при желании — упрощённый Gantt или тепловая карта загрузки по неделям (в часах).

**Критерий успеха:** руководитель или PM за 1–2 минуты видит прогноз загрузки отдела/специалиста на 2–3 месяца и понимает, когда можно брать новый объём работ.

---

### 3.2. Проблема 2: Состояние нагрузки в реальном времени на основе Bitrix24

**Суть:** Загрузка в Bitrix24 меняется каждый день; нужно видеть актуальную картину без ручного переноса данных.

**Решение в продукте:**

- **Синхронизация с Bitrix24:** периодический опрос API **только по задачам** (и данным, необходимым для задач: пользователи, проекты задач, время выполнения, дедлайны) и обновление локальной модели загрузки.
- **«Реальное время»** в условиях REST API: обновление по расписанию (например, каждые 15–30 минут) плюс ручное обновление по кнопке. При наличии webhook Bitrix24 — подписка на события для ускорения.
- **Единая модель:** специалист, отдел, задача, часы — одна модель для прогноза и для «текущей» загрузки. Все значения в **часах**; при отображении можно показывать часы относительно нормы (в т.ч. в виде % для наглядности), но хранение и логика — только в часах.
- **Вид в реальном времени:** дашборд по отделам/специалистам с индикаторами (норма / перегруз / недогруз), список активных задач и **часы** загрузки на текущую неделю/месяц.

**Критерий успеха:** при открытии приложения пользователь видит актуальную (на момент последней синхронизации) загрузку, согласованную с задачами в Bitrix24.

## 4. Функциональные блоки (кратко)

1. **Справочники и настройки**
   - **Специалисты и отделы** — по возможности автоматически из Bitrix24 (пользователи, структура); при необходимости — минимальная ручная настройка (привязка пользователя Bitrix24 к отделу, к типу направления: SEO, разработка, дизайн).
   - **Лимиты часов по типам работ:** у каждого специалиста задаются лимиты в часах (например, в день или в неделю) на **флайт-проекты** (разовые работы) и, по сути, остаток — на **регулярные услуги**. Пример: 6 ч/день на флайты, остальные 2 ч — на регулярку. Это нужно для фуллстеков и тех, кто совмещает оба типа работ.
   - Настройки интеграции: портал Bitrix24, права доступа, периодичность синхронизации.
   - Нормы загрузки в **часах** (рабочие часы в день/неделю/месяц) для сравнения с фактом и планом.

2. **Интеграция с Bitrix24 (только задачи и связанные данные)**
   - Автоматическая загрузка и обновление: **задачи** (ответственный, сроки, оценка/факт времени, статус, проект задачи), **пользователи** (сотрудники), при необходимости — **проекты задач** и **время выполнения** по задачам. Другие сущности Bitrix24 не используются.
   - Маппинг пользователей Bitrix24 → специалисты/отделы в приложении (по возможности автоматически по структуре Bitrix24).
   - Учёт оставшихся трудозатрат по задачам в часах (план/факт из API).
   - Синхронизация по расписанию + ручной запуск; минимизация ручного ввода — все данные, которые Bitrix24 отдаёт по задачам и сотрудникам, подтягиваются автоматически.

3. **Планирование и сетка по дням (основной экран)**
   - **Сетка (шахматка):** строки — активные задачи выбранных специалистов (из Bitrix24), колонки — специалист, проект, плановые часы, плановый дедлайн, затем **колонки по рабочим дням** на выбранный период (неделя / месяц / год). В ячейке дня — **часы из Bitrix24** (учёт времени по задаче в этот день), без ручного ввода.
   - Источник данных: задачи Bitrix24 (ответственный, дедлайн, оценка времени) + **учёт времени по задачам** (task.elapseditem в REST API) — кто в какой день сколько минут трекал; данные агрегируются по дню и отображаются в сетке.
   - Опционально: ручные плановые записи как дополнительный слой (внутренние задачи, не отражённые в B24); учёт отпусков и недоступности.
   - Агрегация: специалист → отдел → общая картина. Контроль лимитов по флайтам — по желанию.

4. **Прогноз на 2–3 месяца**
   - Экран(ы): выбор отдела/специалиста, период (недели/месяцы), вид (таблица, тепловая карта, упрощённый Gantt).
   - Расчёт прогноза в **часах**: план из приложения + «оставшиеся» часы из задач Bitrix24 по срокам.
   - Индикация перегруза и недогруза относительно нормы (в часах). При необходимости — контроль лимитов по флайтам/регулярке.

5. **Текущая загрузка (реальное время)**
   - Дашборд: отделы и специалисты, текущая неделя/месяц, **часы** загрузки, статус (норма/перегруз/недогруз).
   - Детализация: список задач из Bitrix24 и плановых позиций по периоду; при необходимости — разбивка по типам работ (регулярка / флайт) и сравнение с лимитами.
   - Фильтры по отделу, специалисту, периоду.

6. **Роли и доступ**
   - **MVP:** доступ к приложению закрыт **.htpasswd** (веб-сервер); своей авторизации, ролей и разграничения прав в приложении нет. Подключение к Bitrix24 — по **токену вебхука** (исходящие запросы к API). Этого достаточно для тестирования силами нескольких коллег.
   - **После MVP:** роль «руководитель отдела», роль «PM», аутентификация (Bitrix24 OAuth или логин/пароль) — по необходимости.

7. **Дополнительный функционал (приоритет по желанию)**
   - Уведомления: перегруз специалиста/отдела, приближение дедлайнов по ключевым задачам.
   - Отчёты и экспорт: загрузка по отделам за период (Excel/PDF).
   - Конфликты и предупреждения: пересечение задач по срокам, превышение 100% загрузки.
   - Обратная связь с Bitrix24: создание/обновление задач из приложения (опционально, для продвинутой версии).

## 5. Архитектура (высокоуровнево)

### 5.1. Общая схема

```
[Пользователь] → [Frontend (Vue.js, HTML/SCSS)] → [Backend API (PHP)] → [MySQL]
                                                                  ↘
                                                          [Сервис синхронизации]
                                                                  ↘
                                                          [Bitrix24 REST API]
```

- **Frontend:** SPA на Vue.js (JavaScript), разметка и стили — HTML/SCSS. Роутинг, состояние (Vuex/Pinia), экраны: дашборд, планирование, прогноз, справочники, настройки.
- **Backend:** PHP. **В MVP — без Laravel:** чистый PHP или микрофреймворк (Slim и т.п.), REST API для фронта, cron для синхронизации с Bitrix24. После MVP при росте функционала можно рассмотреть Laravel/Symfony.
- **БД:** MySQL — специалисты, отделы, плановые записи, кэш задач из Bitrix24, лог синхронизации, настройки интеграции; таблицы пользователей/ролей — после MVP.
- **Интеграция:** cron или простой фоновый скрипт по расписанию и по запросу вызывает Bitrix24 API по токену вебхука, обновляет локальные данные.
- **MVP: доступ** — закрытие приложения через **.htpasswd**; Bitrix24 — по **токену вебхука** (без OAuth и своей авторизации в приложении).

### 5.2. Потоки данных

- **Чтение из Bitrix24:** задачи (и проекты), пользователи, учёт времени по задачам (task.elapseditem). Данные нормализуются и сохраняются в своей БД (кэш + маппинг на специалистов/отделы). Другие сущности Bitrix24 (сделки, лиды, CRM) не используются.
- **Расчёт загрузки:** для каждого специалиста и периода суммируются **часы** из плановых записей и из задач Bitrix24; результат сравнивается с нормой (часы/день, неделю или месяц) и с лимитами по типам работ (флайт/регулярка); отображение в часах и в виде статуса (при желании — дополнительно в % от нормы для наглядности).
- **Запись в Bitrix24:** в первой версии не обязательна; при необходимости — создание/обновление задач через API.

### 5.3. Безопасность и мультитенантность

- Один инстанс приложения может обслуживать несколько «порталов» Bitrix24 (разные агентства/компании): данные изолируются по tenant_id (или аналогу).
- Токены и ключи Bitrix24 хранятся зашифрованно, доступ к API — только с backend.
- Роли и права проверяются на backend при каждом запросе к API планирования и отчётов.

## 6. Интеграция с Bitrix24 — ключевые моменты

- **Используем только задачи и связанные с ними данные.** Другие сущности Bitrix24 (сделки, лиды, контакты, CRM и т.д.) не используются.
- **Методы API:** задачи (`tasks.task.*`, `tasks.task.list` и т.д.), пользователи (`user.*`), при необходимости — проекты задач (`tasks`), тайм-трек по задачам (если есть в API). Всё, что Bitrix24 отдаёт по задачам и сотрудникам — забираем автоматически, чтобы минимизировать ручной ввод.
- **Что забираем автоматически:** список задач (ответственный, сроки, оценка времени план/факт, статус, проект задачи); список сотрудников; **учёт времени по задачам** (task.elapseditem.getlist в REST v2) — записи «кто сколько минут трекал по задаче», с датой (день) для построения сетки по дням. Цель — не дублировать в приложении то, что уже есть в Bitrix24.
- **Маппинг:** по возможности автоматически (пользователь Bitrix24 → специалист, отдел из структуры Bitrix24); при необходимости — минимальная ручная настройка в приложении.
- **Частота:** синхронизация по cron (например, каждые 15–30 минут); при наличии webhook Bitrix24 — подписка на изменения задач.
- **Ошибки и лимиты:** учёт лимитов Bitrix24 API, повторные попытки, логирование ошибок и уведомление администратору при сбоях.

## 7. Модель данных (концептуально)

- **Пользователи приложения** — роли, привязка к Bitrix24 (id пользователя портала).
- **Специалисты** — привязка к пользователю Bitrix24, отдел, норма рабочих часов (день/неделя/месяц), **лимит часов на флайт-проекты** (например, ч/день или ч/неделю); остаток нормы — на регулярные услуги. Активность (включён в планирование или нет).
- **Отделы** — название, тип (SEO, разработка, дизайн), связь со специалистами; по возможности синхронизация из Bitrix24.
- **Типы работ** — регулярные услуги / флайт-проекты (разовые работы); задачи из Bitrix24 при необходимости классифицируются по типу (по проекту, тегу или настройке в приложении), чтобы считать часы в рамках лимитов.
- **Плановые записи** — специалист, период, **часы** (только часы), тип (задача Bitrix24, внутренняя задача, отпуск и т.д.), тип работы (регулярка/флайт) при необходимости, ссылка на задачу Bitrix24.
- **Кэш Bitrix24** — задачи: id, заголовок, ответственный, сроки, оценка/факт времени, проект задачи; **учёт времени по дням**: таблица записей «задача + пользователь + дата (день) + минуты» (из task.elapseditem), чтобы строить сетку «кто сколько трекал в какой день».
- **Настройки интеграции** — портал (URL), токен/ключ приложения, маппинг пользователей и отделов, расписание синхронизации.

## 8. Дополнительный функционал (расширения)

- **Уведомления:** перегруз/недогруз отдела или специалиста, напоминания о сроках ключевых задач; канал — email или уведомления в приложении.
- **Отчёты:** свод по загрузке за месяц/квартал по отделам, экспорт в Excel/PDF.
- **Валидация и конфликты:** предупреждение при превышении нормы часов на период, при превышении лимита часов на флайты у специалиста, при пересечении сроков одних и тех же ресурсов.
- **Обратная запись в Bitrix24:** создание задачи из планировщика с подстановкой ответственного и срока (опционально).
- **Мобильная адаптация:** responsive-интерфейс для просмотра дашборда и прогноза с планшета/телефона.

## 9. Нефункциональные требования

- **Доступность:** целевой uptime 99% и выше (зависит от хостинга).
- **Производительность:** открытие дашборда и прогноза — не более 2–3 секунд при типичном объёме данных (десятки специалистов, сотни задач).
- **Масштабируемость:** архитектура допускает увеличение числа порталов Bitrix24 и объёма синхронизируемых задач за счёт очередей и оптимизации запросов к API и БД.
- **Безопасность:** HTTPS, хранение токенов в зашифрованном виде, разграничение прав по ролям, аудит критичных действий (опционально).

## 10. Риски и допущения

- **Допущения:** Bitrix24 — единственный источник данных по задачам и сотрудникам; ручной ввод сведён к минимуму (нормы/лимиты часов, при необходимости — привязка типа задачи к регулярке/флайту). Маппинг пользователей и отделов по возможности автоматический из Bitrix24.
- **Риски:** ограничения и изменения Bitrix24 API, лимиты по запросам; расхождение между планом в приложении и задачами в Bitrix24 — минимизируется за счёт автоматической синхронизации и явного отображения источника.
- **Зависимости:** стабильная работа портала Bitrix24; права приложения на чтение задач и пользователей.

## 11. Этапы реализации (предварительно)

1. **Фаза 0:** Уточнение ТЗ с заказчиком — роли, список полей из Bitrix24, приоритеты по экранам.
2. **Фаза 1:** Справочники (специалисты, отделы), настройка интеграции, базовая синхронизация задач и пользователей Bitrix24.
3. **Фаза 2:** Планирование (ввод плановых трудозатрат), расчёт загрузки по специалистам и отделам.
4. **Фаза 3:** Экран прогноза на 2–3 месяца и дашборд «текущей» загрузки.
5. **Фаза 4:** Роли, права, уведомления, отчёты и экспорт — по приоритету.
6. **Фаза 5:** Доп. функции (обратная запись в Bitrix24, углублённая аналитика) — по необходимости.

- **Реализовано:** Фазы 0–1 (справочники, интеграция, синхронизация задач/пользователей/учёта времени), Фаза 2 (плановые записи, расчёт загрузки, типы работ по проектам B24), перепланирование ПМ (task_plan_override, task_plan_daily, сетка с исходным планом/перепланом/фактом), экран загрузки (дашборд по специалисту/отделу), сетка планирования (шахматка по дням).
- **В плане:** экран «Прогноз» на 2–3 месяца (Фаза 3.1), доработка дашборда (время последней синхронизации, ссылки на B24), валидация/уведомления/отчёты (Фаза 4), роли и мультитенантность (Фаза 5).

Документ можно дополнять разделами: детальная схема БД, макеты экранов, список методов Bitrix24 по этапам, критерии приёмки по фичам.
